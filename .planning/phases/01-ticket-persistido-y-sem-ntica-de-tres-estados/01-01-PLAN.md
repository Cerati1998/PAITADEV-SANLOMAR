<objective>
Crear el vocabulario de estado persistible de la comunicación de baja y el servicio
que concentra toda la semántica del ticket: persistir el ticket antes de consultar,
clasificar el desenlace en aceptada / pendiente / rechazada, archivar el CDR y
marcar los comprobantes.

Este plan produce la pieza de dominio que los dos llamadores duplicados
(`VoidedForm::send()` y `VoidedTable::sendXml()`) consumirán en los planes 02 y 03,
que es lo que exige D-11: el defecto vive por partida doble porque el flujo está
copiado en dos sitios.

Purpose: hoy el ticket vive solo en una variable local, se pierde si la consulta de
estado falla, y el fallo se escribe como rechazo — de modo que el sistema contradice
a SUNAT y el listado ofrece reenviar un XML que SUNAT ya recibió (error `2109`).
Output: enum `VoidedStatus`, columnas `voideds.sunat_ticket` / `voideds.sunat_status`,
cast en el modelo, y el servicio `VoidedTicketFlowService`.
</objective>

**Método público `sendAndResolve(Voided $voided, string $xml, string $cdrPath): VoidedStatus`**

   Si lanza, clasifica rechazada (D-06: el envío falló antes de devolver ticket) con un

   `$this->util->getErrorResponse($result)` como `sunatResponse`. D-06: sin ticket.
4. Lee el ticket del resultado. Si viene vacío, clasifica rechazada con un mensaje

**Método público `resolveTicket(Voided $voided, string $cdrPath, ?See $see = null): VoidedStatus`**

Se expone público a propósito: D-11 fija que la Fase 2 debe encontrar esta pieza hecha
cuando reescriba la reconsulta del listado. En esta fase su único llamador es
`sendAndResolve()`. Importar `Greenter\See` para el tipo del tercer parámetro; si llega
`null`, construir el cliente con `$this->util->getSee()`.

1. Lee el ticket de `$voided->sunat_ticket`.
2. Envuelve `$see->getStatus($ticket)` en su propio `try { } catch (\Throwable $e) { }`.
   Esto es obligatorio y no es equivalente a comprobar el éxito del resultado:
   `ExtService::getStatus()` de Greenter solo atrapa `SoapFault`, y una respuesta HTTP 200
   con cuerpo mal formado lanza `Greenter\Services\InvalidServiceResponseException` (que
   extiende `LogicException`, no `SoapFault`) y escapa sin atrapar. Si escapara aquí, la
   anulación terminaría escrita como rechazo silencioso — exactamente el defecto que
   esta fase elimina. En el `catch`, clasifica pendiente con motivo `'fallo_transporte'`,
   código `null` y el mensaje de la excepción. Cubre TICKET-03 y D-05.
3. Lee el ZIP del CDR y el objeto CDR del resultado. **Si ambos vienen vacíos**, clasifica
   pendiente (TICKET-02, D-05). El motivo se deriva del código de error recibido: si es
   exactamente `'98'`, motivo `'codigo_98'`; en cualquier otro caso, motivo
   `'fallo_transporte'`. Esta derivación es solo para el detalle informativo de D-04 —
   la decisión de clasificar como pendiente NO depende de ella y NO hay lista blanca de
   códigos ni de mensajes (D-05). El código de error puede no ser una cadena vacía: para
   un fallo de transporte Greenter deja el `faultcode` crudo, así que no escribir ninguna
   comparación que espere cadena vacía.
4. **Si hay ZIP de CDR, archivarlo siempre**, sin importar el indicador de éxito del
   resultado: asignar `$voided->cdr_path = $cdrPath` y `Storage::put($cdrPath, $zip)`.
   Motivo (RESEARCH Pitfall 4): un CDR puede venir poblado y aun así el resultado
   reportar fallo, cuando el código propio del CDR cae en el rango de excepción 100-1999

   criterio 4 de la fase. Si el código es `0`: `sunatResponse` = `$this->util->readCdr($cdr)`,

**Método público `classifyFailure(Voided $voided, \Throwable $e): VoidedStatus`**

Existe para que los dos llamadores Livewire (planes 02 y 03) NO reimplementen la regla
de clasificación en su `catch (\Throwable)` exterior, que es donde el flujo actual
escribe el rechazo silencioso. Aplica la regla fiable de RESEARCH Pitfall 3 — la
clasificación no depende del contenido del error sino de si ya existe un ticket
persistido en ese punto:

- Si `$voided->sunat_ticket` es `null`, delega en `markRejected()` con
  `['success' => false, 'error' => ['code' => null, 'message' => $e->getMessage()]]`.
  Es el caso D-06: el fallo ocurrió antes de que SUNAT devolviera ticket.
- Si `$voided->sunat_ticket` tiene valor, delega en `markPending()` con motivo
  `'fallo_transporte'`, código `null` y el mensaje de la excepción. Cubre el caso en que
  una excepción escape después de que el ticket ya se guardó (por ejemplo un fallo de
  `Storage::put` al archivar el ZIP del CDR): SUNAT ya recibió el XML, de modo que
  escribir rechazo ahí reintroduciría exactamente el defecto que esta fase elimina.

**Métodos privados de clasificación** (un único punto de escritura por desenlace):

- `markPending(Voided $voided, string $reason, ?string $code, ?string $message): VoidedStatus`
  escribe `sunat_status = VoidedStatus::Pendiente`, **no toca `sunat_ticket`** (queda
  guardado) y escribe un `sunatResponse` explícito de pendiente — nunca `null`, porque
  `null` sería indistinguible de "nunca se envió" (D-04). Forma exacta del JSON:
  clave `success` en `false` para mantener la forma compatible con las otras dos ramas, y
  una clave `pending` con las subclaves `reason` (valores `'codigo_98'` o
  `'fallo_transporte'`), `code` y `message`. Registrar además un `Log::warning` con el
